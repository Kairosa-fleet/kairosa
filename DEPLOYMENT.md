# Deployment — free testing-phase setup

Backend on **Render**, web on **Vercel**, database on **Neon**, Redis on
**Upstash**. Every push to `main` auto-deploys the backend and the web app —
both providers do this natively, so there is no GitHub Actions pipeline to
maintain. The Android app is built locally and shared as an APK.

Total cost: **₹0** for the testing phase. The trade-offs that buys are listed
under "What 'free' costs you" at the bottom — read them, they are real.

---

## The stack, and why each piece

| Layer | Service | Free tier | Why this one |
|---|---|---|---|
| Backend API | Render (Docker web service) | 750 hrs/mo, spins down after 15 min idle | Native Docker + auto-deploy from GitHub |
| Web dashboard | Vercel (Hobby) | 100 GB transfer/mo | Native Next.js + auto-deploy. **See commercial-use note.** |
| Database | **Neon** Postgres | 0.5 GB, permanent, **PostGIS included** | Render's own free Postgres **expires in 30 days**; Neon does not, and this app needs PostGIS |
| Redis | **Upstash** | 500 K commands/mo | Rate limits, live-map fan-out, geocode cache |
| Maps/geocoding | MapTiler | 100 K loads/mo | Already integrated and working |
| Routing | OSRM public demo | free, no key | Fine for testing; self-host later |

> **Deliberately not using Render's Postgres or Key-Value.** Both are free but
> **expire after 30 days**. Neon + Upstash are free *indefinitely*, so your
> test data does not evaporate mid-testing.

## One-time setup (about 30 minutes)

Do these in order — the backend must exist before the web app can point at it.

### 1. Database — Neon

1. Sign up at neon.tech → create a project (region: **Singapore/Mumbai**).
2. In the project's **SQL Editor**, run once: `CREATE EXTENSION postgis;`
3. Copy the **pooled** connection string. It looks like
   `postgresql://user:pass@ep-xxx.aws.neon.tech/dbname?sslmode=require`.
4. Change the scheme to `postgresql+asyncpg://…` (this app uses the async
   driver) and **keep `?sslmode=require`**. Hold onto this — it is `DATABASE_URL`.

### 2. Redis — Upstash

1. Sign up at upstash.com → create a Redis database (region near India).
2. Copy the connection URL (starts `rediss://`). This is `REDIS_URL`.

### 3. Backend — Render

1. Push this repo to GitHub. Edit `render.yaml` line `repo:` to your repo URL.
2. Render dashboard → **New → Blueprint** → pick the repo. It reads
   `render.yaml` and creates the `fleet-backend` service.
3. When prompted, paste the `sync: false` secrets:
   - `DATABASE_URL` — from Neon (step 1)
   - `REDIS_URL` — from Upstash (step 2)
   - `MAPTILER_KEY` — from your MapTiler account
   - `CORS_ORIGINS` and `PUBLIC_WEB_URL` — **leave as a placeholder for now**
     (e.g. `https://example.vercel.app`); you will set the real Vercel URL in
     step 5.
   - `JWT_SECRET` is generated by Render automatically — do nothing.
4. Deploy. When it is live, note the URL: `https://fleet-backend-xxxx.onrender.com`.
   Check `https://<that-url>/health` returns `{"status":"ok"}`.

### 4. Web — Vercel

1. Vercel dashboard → **Add New → Project** → import the same GitHub repo.
2. **Root Directory: `web`** (this is a monorepo; Vercel must build only `web`).
   Framework "Next.js" is auto-detected.
3. Add environment variables (all are public `NEXT_PUBLIC_*` — safe to expose):

   | Variable | Value |
   |---|---|
   | `NEXT_PUBLIC_API_BASE_URL` | your Render URL, e.g. `https://fleet-backend-xxxx.onrender.com` |
   | `NEXT_PUBLIC_WS_BASE_URL` | same host with `wss://`, e.g. `wss://fleet-backend-xxxx.onrender.com` |
   | `NEXT_PUBLIC_MAP_PROVIDER` | `maptiler` |
   | `NEXT_PUBLIC_MAPTILER_KEY` | your MapTiler key |

4. Deploy. Note the URL: `https://fleet-xxxx.vercel.app`.

### 5. Close the loop — point the backend at the web app

1. Back in Render → `fleet-backend` → Environment, set the real values:
   - `CORS_ORIGINS` = `https://fleet-xxxx.vercel.app`
   - `PUBLIC_WEB_URL` = `https://fleet-xxxx.vercel.app`
2. Save → Render redeploys. Done.

Open the Vercel URL, register your organisation, fill **Settings → letterhead**,
and you are live.

### 6. Android APK (personal sharing)

The backend URL is **baked into the APK at build time**, so build it pointing
at Render:

```bash
cd mobile
EXPO_PUBLIC_API_BASE_URL=https://fleet-backend-xxxx.onrender.com \
EXPO_PUBLIC_WS_BASE_URL=wss://fleet-backend-xxxx.onrender.com \
EXPO_PUBLIC_MAPTILER_KEY=<your-key> \
  npx expo run:android --variant release
# APK: mobile/android/app/build/outputs/apk/release/app-release.apk
```

Share that file directly (Drive/WhatsApp). No `adb reverse` needed now — the
app talks to the public HTTPS backend. The cleartext-HTTP restriction we built
in is satisfied because Render is HTTPS.

## Auto-deploy — already on

Once the repos are connected there is nothing else to configure:

- **Push to `main`** → Render rebuilds the backend, runs `alembic upgrade head`,
  goes live.
- **Push to `main`** → Vercel rebuilds and deploys the web app.
- Pull-request branches get Vercel **preview URLs** automatically (those won't
  pass CORS unless you add them to `CORS_ORIGINS` — fine to ignore for testing).

## What "free" costs you (read this)

1. **Backend cold starts.** Render free spins the API down after 15 min idle;
   the next request waits ~50 s while it wakes. For a live-tracking app that is
   noticeable but acceptable for testing. (Fix later: $7/mo Render Starter, or a
   cron ping every 14 min to keep it warm.)

2. **Uploaded files** — **now solved with Cloudflare R2** (see "Object
   storage" below). Without R2 configured the backend falls back to local disk,
   which on Render is ephemeral (every deploy wipes the scans); with the four
   `S3_*` env vars set, uploads go to R2 and persist. Set them and this is a
   non-issue.

3. **Vercel Hobby is non-commercial only.** Their terms restrict Hobby to
   "non-commercial personal use." A testing phase with no payments and personal
   APK sharing is a practical grey area, but once this is a live business tool
   it needs **Vercel Pro ($20/mo)** — or deploy the web app as a **Render Static
   Site** (also free, no commercial clause) to sidestep it entirely.

4. **Neon/Upstash scale to zero** after ~5 min idle too, adding ~0.5 s to the
   first query. Negligible next to the Render cold start.

## Object storage — Cloudflare R2 (persistent document uploads)

Free: 10 GB storage, zero egress fees. This is what keeps vehicle/driver
document scans, LR PDFs and e-way-bill images alive across redeploys. The app
stores each object namespaced by organization and serves it back through the
authenticated, org-scoped download endpoint — files are never public.

1. Cloudflare dashboard → **R2** → **Create bucket** → name it
   `kairosa-documents` (region: Automatic).
2. R2 → **Manage R2 API Tokens** → **Create API token** → permission
   **Object Read & Write**, scoped to that bucket → Create. Copy the
   **Access Key ID** and **Secret Access Key** (shown once).
3. On the R2 overview, note your **S3 API endpoint**:
   `https://<accountid>.r2.cloudflarestorage.com`.
4. In Render → kairosa-backend → Environment, set:

   | Key | Value |
   |---|---|
   | `S3_ENDPOINT_URL` | `https://<accountid>.r2.cloudflarestorage.com` |
   | `S3_BUCKET` | `kairosa-documents` |
   | `S3_ACCESS_KEY_ID` | the Access Key ID |
   | `S3_SECRET_ACCESS_KEY` | the Secret Access Key |

   Save → Render redeploys. Uploads now persist. (Leave all four unset locally
   and the app uses the disk under `UPLOAD_DIR` — no R2 account needed for dev.)

## Recommendation

Start exactly as above — it is genuinely free and auto-deploying. Before you put
**real customer documents** in, do two things: wire **Cloudflare R2** for
uploads (gotcha #2), and decide Vercel Pro vs Render Static for the web
(gotcha #3). Everything else scales fine on free for a real pilot.
